# Grok 4.6（global.xai.grok-4.6）モデル対応 設計書

## 背景・目的

xAI の Grok 4.6 が 2026-08-18 に Amazon Bedrock で一般提供開始された。本アプリの選択可能モデル一覧（`AVAILABLE_MODEL_KEYS` / `type_model_name`）には未登録であり、UI から選択できない。

Grok 4.6 は Claude 系と異なる制約を複数持つため、既存モデルと同じ扱いでは動作しない。本設計では、実際に AWS 環境（アカウント 985124897484 / プロファイル `acrocity-rag-system`）へ API を発行して確認した挙動を根拠に、必要な差分を定義する。

### 実測で確認した挙動

検証は `ap-northeast-1`（東京）に対し `global.xai.grok-4.6` を指定して実施した。

動作するもの:

- `Converse` / `ConverseStream` の両方
- ツール呼び出し。`toolConfig` を渡すと `stopReason: tool_use` と `toolUse` ブロックが返る
- ツールループ2ターン目（`toolResult` の返却）。`reasoningContent` ブロックを保持した場合と除去した場合の両方で成功する
- `system` プロンプトの複数コンテンツブロック
- assistant プレフィル
- 画像入力（64x64 PNG で成功）
- `additionalModelRequestFields` 経由の reasoning effort 指定

動作しないもの（いずれも `ValidationException` などで明示的に拒否される）:

- `inferenceConfig.temperature` — `This model doesn't support the temperature field.`
- `inferenceConfig.topP` — `This model doesn't support the topP field.`
- `inferenceConfig.stopSequences` — `This model doesn't support the stopSequences field.`（空配列を渡した場合も同じエラー）
- `document` コンテンツブロック — `This model doesn't support documents.`
- プロンプトキャッシュ（`cachePoint`）— `AccessDeniedException`。AWS のモデルカードには対応と記載があるが、実際には拒否された
- 素のモデルID `xai.grok-4.6` での呼び出し — `Invocation of model ID xai.grok-4.6 with on-demand throughput isn't supported.` 推論プロファイル経由でのみ呼び出せる
- `ap-northeast-1` からの `us.xai.grok-4.6` — `The provided model identifier is invalid.` 東京リージョンは Global プロファイルのみ利用できる

### reasoning effort の指定形式

正しい形式は `additionalModelRequestFields={"reasoning": {"effort": <値>}}` である。根拠は以下の2点。

- 値に不正な文字列を入れると `ValidationException`（`invalid_value`）で拒否される。すなわちこのフィールドはモデル側でバリデーションされている
- `effort` を `low` と `xhigh` で切り替えると出力トークン数が 295 → 583 と約2倍に変化する

一方 `additionalModelRequestFields={"reasoning_effort": "high"}` はエラーにならないが、値を変えても出力トークン数がほぼ変化しない。対照実験として `{"bogus_xyz": 1}` も同様にエラーなく通ることを確認しており、未知のトップレベルフィールドは単に無視されていると判断した。この形式は採用しない。

## 設計方針

`backend/app/bedrock.py` に既に存在するモデルファミリ別の分岐機構（`is_nova_model` / `is_deepseek_model` / `is_gpt_oss_model` など）と、`GLOBAL_INFERENCE_PROFILES` によるプロファイル解決機構をそのまま利用する。GPT-OSS 追加時（PR #924）と同じ8ファイル構成を踏襲し、CDK 側の変更は行わない。

モデルキーは `grok-4.6` とする。フロントエンドの `toCamelCase`（`frontend/src/utils/StringUtils.ts`）を通すと `grok46` となり、既存の `ActiveModels` キーと衝突しない。

## バックエンド変更

### モデル名の型定義

`backend/app/routes/schemas/conversation.py` の `type_model_name` Literal に `"grok-4.6"` を追加する。既存の Mistral / Nova / DeepSeek などと同様に、xAI 用のセクションコメントを添える。

### モデルIDとプロファイル定義

`backend/app/bedrock.py` に以下を追加する。

- `BASE_MODEL_IDS` に `"grok-4.6": "xai.grok-4.6"` を追加する。既存の `get_global_inference_profile_id` が `f"global.{base_model_id}"` を組み立てるため、これだけで `global.xai.grok-4.6` が生成される。
- `GLOBAL_INFERENCE_PROFILES` に `"grok-4.6"` を追加する。`supported_regions` には Global クロスリージョン推論に対応する全リージョンを列挙する（`us-east-1`, `us-east-2`, `us-west-1`, `us-west-2`, `ca-central-1`, `ca-west-1`, `eu-central-1`, `eu-central-2`, `eu-north-1`, `eu-south-1`, `eu-south-2`, `eu-west-1`, `eu-west-2`, `eu-west-3`, `ap-east-2`, `ap-northeast-1`, `ap-northeast-2`, `ap-northeast-3`, `ap-south-1`, `ap-south-2`, `ap-southeast-1`, `ap-southeast-2`, `ap-southeast-3`, `ap-southeast-4`, `ap-southeast-5`, `ap-southeast-6`, `ap-southeast-7`, `il-central-1`, `me-central-1`, `me-south-1`, `af-south-1`, `sa-east-1`）。
- `REGIONAL_INFERENCE_PROFILES` に `"grok-4.6"` を追加する。Geo クロスリージョン推論は US ジオのみ対応するため、`{"us-east-1": "us", "us-east-2": "us", "us-west-1": "us", "us-west-2": "us"}` とする。

### 推論プロファイルの強制

Grok 4.6 はオンデマンドスループットでの呼び出しに対応しない。現行の `get_model_id`（`backend/app/bedrock.py:1595`）は、Global もクロスリージョンも利用できない場合に素の `base_model_id` を返す設計であり、`ENABLE_BEDROCK_GLOBAL_INFERENCE` と `ENABLE_BEDROCK_CROSS_REGION_INFERENCE` がいずれも無効な環境では必ず呼び出しが失敗する。

これを防ぐため、モジュールレベルに定数 `PROFILE_REQUIRED_MODELS: set[type_model_name] = {"grok-4.6"}` を新設する。`get_model_id` の先頭、すなわち Global 判定（`enable_global`）とクロスリージョン判定（`enable_cross_region`）の両方より前で、対象モデルがこの集合に含まれるかを判定する。含まれる場合は環境変数フラグの値に関係なく `get_global_inference_profile_id` を呼び、得られたプロファイルIDを返す。

この判定をクロスリージョン試行より前に置くのは料金計算の一意性のためである。`calculate_price`（`backend/app/bedrock.py`）はデプロイ先リージョンをキーに `BEDROCK_PRICING` を参照するのみで、実際にどの推論プロファイル（Global / クロスリージョン地域別）が使われたかを知る手段を持たない。仮にクロスリージョン判定を先に通してしまうと、`ENABLE_BEDROCK_GLOBAL_INFERENCE` が無効かつ `ENABLE_BEDROCK_CROSS_REGION_INFERENCE` が有効な環境（米国リージョンの公開APIスタックがこれに該当する）では地域別プロファイル `us.xai.grok-4.6` が選ばれてしまい、Global 料金しか持たない `BEDROCK_PRICING` の `default` エントリと実際の課金（地域別料金は Global よりわずかに高い）がずれる。判定を先頭に置き、地理的フォールバックを一切持たせないことで、Grok は常に Global プロファイルにのみ解決されるという不変条件が保証され、料金の対応関係が一意になる。この不変条件を崩す「地理的フォールバックの追加」は意図的に行わない。

現在のリージョンが Global プロファイル非対応だった場合は、素のモデルIDを返しても確実に失敗するため、`ValueError` を送出して原因が判別できるメッセージを残す。

### 推論パラメータの構築

`_prepare_grok_model_params(model, generation_params)` を新設する。返す `ConverseConfiguration` は以下とする。

- `inferenceConfig` には `maxTokens` のみを設定する。`temperature` / `topP` / `stopSequences` はモデルが拒否するため一切含めない
- `additionalModelRequestFields` に `{"reasoning": {"effort": "low"}}` を設定する。`low` は Bedrock 側の既定値と一致する

`generation_params_to_converse_configuration`（`backend/app/bedrock.py:1195`）のファミリ分岐に `is_grok_model(model)` の枝を追加し、この関数を呼ぶ。既存の Nova / DeepSeek / Llama / Mistral / GPT-OSS の分岐と同じ位置に置く。

### モデルファミリ判定と機能フラグ

`is_grok_model(model)` を追加する。実装は既存の同種関数に合わせ `return "grok" in model` とする。

機能フラグ関数は判定方式が2種類あるため、方式ごとに扱いを分ける。

`model not in [...]` 形式（除外リスト）の関数のうち、以下は除外リストに `"grok-4.6"` を追加して `False` を返すようにする。

- `is_temperature_supported`
- `is_top_p_supported`
- `is_top_k_supported`
- `is_specify_both_temperature_and_top_p_supported`

`model in [...]` 形式（包含リスト）の関数は、`"grok-4.6"` を追加しないことで `False` となる。いずれも意図的に追加しない。

- `is_prompt_caching_supported` — `system` / `message` / `tool` のすべての target で `False` となる。実測でプロンプトキャッシュが `AccessDeniedException` となるため
- `is_adaptive_thinking_model` — Claude 専用の `thinking: {"type": "adaptive"}` を送ってはならないため

以下は変更を加えず、既定で `True` となる。いずれも実測で動作を確認している。

- `is_tooluse_supported` — 除外リスト形式。追加しないことで `True`
- `is_prefill_supported` — 同じく除外リスト形式。追加しないことで `True`
- `is_multiple_system_prompt_content_supported` — Nova / DeepSeek / Llama / Mistral / GPT-OSS のいずれにも該当しないため `True`
- `is_unsigned_reasoning_content_supported` — DeepSeek / GPT-OSS のいずれにも該当しないため `True`

### reasoning コンテンツの扱い

Grok は思考内容を `reasoningContent.redactedContent`（暗号化されたバイト列）として返す。Claude の `reasoningContent.reasoningText` とは形式が異なるが、本アプリは既に `redactedContent` を扱える。

- `ReasoningContentModel.redacted_content`（`backend/app/repositories/models/conversation.py:600`）に格納フィールドが存在する
- `to_contents_for_converse`（同 610 行）が `redactedContent` を出力する
- ストリーミング受信側（`backend/app/stream.py:261`）が `redactedContent` を読み取る
- Strands 経路のコンバータ（`backend/app/strands_integration/converters/content_converter.py:248`）も対応済み

したがって reasoning に関する追加実装は不要である。`redactedContent` は復号できないため思考本文が UI に表示されることはないが、ブロックの往復は成立する。実測でも reasoning ブロックを保持した場合と除去した場合の双方でツールループ2ターン目が成功している。

### 料金定義

`backend/app/config.py` の `BEDROCK_PRICING` の `default` セクションに `"grok-4.6": {"input": 0.002, "output": 0.006}` を追加する。単位は既存定義と同じ USD / 1,000 トークンで、Global クロスリージョン推論の料金（入力 2.00 USD、出力 6.00 USD / 100万トークン）に対応する。

前節の通り `PROFILE_REQUIRED_MODELS` の判定をクロスリージョン試行より前に置いたことで、Grok は環境変数フラグの組み合わせによらず常に Global プロファイル経由で呼び出される。これは自明な性質ではなく、この判定順序があるからこそ成立する不変条件である。この不変条件により、全リージョンで Global 料金のみが実効となることが保証され、リージョン別セクション（`us-east-1` / `us-west-2`）への追加は不要になる。`calculate_price` はリージョン別定義に該当キーがなければ `default` を参照するため、これで正しい価格が適用される。逆に、もし判定順序が崩れて地域別プロファイルが選ばれる経路が残ると、`calculate_price` はデプロイ先リージョンしか見ないためそれを検知できず、`default` の Global 料金で誤って計算してしまう。

プロンプトキャッシュは利用できないため `cache_write_input` / `cache_read_input` は定義しない。`calculate_price` は該当キーがない場合に入力価格で代替する実装だが、キャッシュトークン数は常に 0 となるため計算結果に影響しない。

## フロントエンド変更

### モデルキーの登録

`frontend/src/constants/index.ts` の `AVAILABLE_MODEL_KEYS` に `'grok-4.6'` を追加する。`frontend/src/@types/conversation.d.ts` の `Model` 型と `frontend/src/@types/bot.d.ts` の `ActiveModels` は同配列から導出されるため、型定義側の変更は不要である。

### モデル定義

`frontend/src/hooks/useModel.ts` の `availableModels` に以下のエントリを追加する。

```
{
  modelId: 'grok-4.6',
  label: t('model.grok-4.6.label'),
  description: t('model.grok-4.6.description'),
  supportMediaType: GROK_SUPPORTED_MEDIA_TYPES,
  supportReasoning: true,
  forceReasoningEnabled: true,
}
```

`GROK_SUPPORTED_MEDIA_TYPES` は同ファイル上部の既存定数群（`CLAUDE_SUPPORTED_MEDIA_TYPES` など）に倣い、`image/jpeg` / `image/png` / `image/gif` / `image/webp` を並べて新設する。

`forceReasoningEnabled: true` は DeepSeek R1 と GPT-OSS で採用されている指定であり、reasoning が常時有効なモデルに対応する。Grok も reasoning を無効化できないためこれに該当する。

### 表示文字列

`frontend/src/i18n/en/index.ts`、`frontend/src/i18n/es/index.ts`、`frontend/src/i18n/ja/index.ts` の `model` セクションに `'grok-4.6'` の `label` と `description` を追加する。`label` は `Grok 4.6` とし、`description` には 500K トークンのコンテキストウィンドウとエージェント用途向けである点を記述する。

対象を3言語に限るのは、直近の GPT-OSS 追加（PR #924）が en / es / ja のみを更新している前例に合わせるためである。未定義の言語では i18n のフォールバックが機能する。

## テスト

`backend/tests/test_bedrock.py` に既存の `test_get_model_id_*` 系および Converse 設定系のテストと同じ形式で追加する。

- `ENABLE_BEDROCK_GLOBAL_INFERENCE` と `ENABLE_BEDROCK_CROSS_REGION_INFERENCE` の双方を無効にした状態でも、`grok-4.6` に対して `get_model_id` が `global.xai.grok-4.6` を返すこと
- Global プロファイル非対応リージョンを指定した場合に `ValueError` が送出されること
- `generation_params_to_converse_configuration` が `grok-4.6` に対して `temperature` / `topP` / `stopSequences` を含まない `inferenceConfig` を返し、かつ `additionalModelRequestFields` に `{"reasoning": {"effort": "low"}}` を含むこと
- `is_prompt_caching_supported` が `grok-4.6` に対して `system` / `message` / `tool` のすべてで `False` を返すこと

## 本設計に含めないもの

- reasoning effort を UI から選択する機能。`low` 固定とする。フロントエンドの型・状態管理・i18n・ボット設定スキーマまで波及するため、必要になった時点で別途検討する
- プロンプトキャッシュ対応。実測で `AccessDeniedException` となるため、Bedrock 側で利用可能になってから対応する
- document（ファイル添付）入力。モデルが非対応
- en / es / ja 以外の13言語の翻訳追加
- CDK の変更。モデル定義は CDK 側に存在しないため不要
